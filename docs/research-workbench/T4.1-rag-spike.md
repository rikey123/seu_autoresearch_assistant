## 2. 真实 paper-qa API 面与关键坑（均已内化到适配器/服务端/测试）

适配器：`docs/research-workbench/sidecars/paperqa-sidecar.py`（部署材料，随分支入库）。

1. **入库元数据查询**：默认 `use_doc_details=True` 会在 intake 时调 Semantic Scholar，实测被 429 限流。适配器设 `use_doc_details=False` 且显式传 `citation=""`，入库零外部调用。
2. **索引不依赖 embedding API**：`parsing.defer_embedding=True`，`docs.aadd()` 纯本地解析 PDF；chunk 数经 `len(docs.texts)` 取得（实测单页 PDF → 1 chunk）。
3. **litellm 模型名需要 provider 前缀**：裸自定义 embedding 模型名会报 `LLM Provider NOT provided`。适配器对无 `/` 的 `RAG_EMBEDDING_MODEL` 自动加 `openai/` 前缀，litellm 即走 `OPENAI_BASE_URL` 的 OpenAI 兼容端点。
4. **litellm 会在 stdout 打 Provider List 横幅**（provider 回退时），污染"stdout 单一 JSON"契约。双保险：适配器设 `litellm.suppress_debug_info = True`；服务端 `parseSidecarStdout` 取 stdout 中**最后一个**可解析且带 `status` 字段的 JSON 对象（有单测钉死）。
5. **Windows 管道截断**：sidecar 在 `stdout.write` 回调里立即 `process.exit()` 会丢数据（libuv 管道写回调先于内核缓冲落盘）。协议文档明确要求"写完自然退出"；测试 stub 与真实适配器均遵守。
6. **pypdf 需要结构完整 PDF**：手写的极简单行 PDF 会被 pypdf 判为 corrupt；门控测试改用结构合法的最小 PDF（含 xref/trailer）。

## 3. 生产调用方式（已实现）

- **sidecar 子进程 + JSON stdio 协议**（钉死在测试）：
  - 请求（stdin，单个 JSON，写入后关闭）：`{"action":"index"|"ask","papers":[{"id","title","path"}],"question":"..."}`（ask 带 question）
  - 响应（stdout，最后一个 JSON 对象为准；日志一律走 stderr）：
    - index：`{"status":"ok","action":"index","chunks":N,"engine":"paper-qa"}`
    - ask：`{"status":"ok","action":"ask","answer":"...","citations":[{"paperId","page","snippet"}],"engine":"paper-qa"}`
    - 失败：`{"status":"error","error":"..."}` 或非零退出码（服务端把 stderr/STDOUT 尾部记入任务 error）
- **入口解析**（服务端 `rag-sidecar.ts`）：`RAG_SIDECAR_BIN` 指向 `.js/.cjs/.mjs`（用当前 Node 跑，测试 stub 路径）、`.py/.pyw`（用 `RAG_SIDECAR_PYTHON` 跑，生产路径）、或直接可执行文件。
- **API-first 配置**（仅环境变量，密钥不落盘）：`OPENAI_API_KEY`（必填，缺则任务 503 明确失败）、`OPENAI_BASE_URL`、`OPENAI_MODEL`、`RAG_EMBEDDING_MODEL`。子进程环境只透传这几个钉死的变量。
- **进程安全**（对照 BC-5/latex 标准）：结构化 argv + `shell:false`；超时（`RAG_SIDECAR_TIMEOUT_MS`，默认 10min）杀整棵进程树（`taskkill /T /F`，有测试断言父子进程双亡）；单次结算；索引/问答共享串行队列；退出兜底 kill。

## 4. 真实链路验证（证据）

门控测试 `rag real paper-qa chain (gated)`（`RAG_SIDECAR_E2E_BIN`/`RAG_SIDECAR_E2E_PYTHON` + 真实 `OPENAI_API_KEY`/`OPENAI_BASE_URL` 齐备才跑）：

- 输入：结构合法的最小英文 PDF（"The research workbench indexes academic papers..."）经 T3.1 论文库上传 → 加入 collection
- `POST /collections/:id/index` → 真实 paper-qa 解析建索引 → job completed（chunks>0，engine=paper-qa）
- `POST /collections/:id/ask` → 本地 OpenAI 兼容端点供 chat+embeddings → question answered，`answer` 为文本，`citations[0].paperId` = 论文 id，snippet 为原文片段
- 实跑结果：**30.3s 通过**（15:15 本机，mock 端点走 HTTP/1.1 thread 模式；paper-qa 并发多个 LLM 调用）

人工复现步骤：

1. 建 Python 3.10–3.12 venv：`pip install paper-qa`（清华镜像）
2. `export RAG_SIDECAR_E2E_BIN=<repo>/docs/research-workbench/sidecars/paperqa-sidecar.py`
3. `export RAG_SIDECAR_E2E_PYTHON=<venv python 绝对路径>`
4. `export OPENAI_API_KEY=... OPENAI_BASE_URL=<OpenAI 兼容端点> OPENAI_MODEL=<chat 模型> [RAG_EMBEDDING_MODEL=<embedding 模型>]`
5. `npx vitest run tests/server/research-rag.test.ts -t "real paper-qa"` 应 1 passed（不设门控时 skipped，CI 零 Python/网络依赖）

## 5. 剩余阻塞与已知限制

- 真实 生产 OpenAI 兼容端点（外部 API 服务商）未在本次 spike 中打（无 key）；本地兼容端点已证协议与 paper-qa 配置正确，换真实端点只差环境变量。
- 持久化索引：当前每次 index/ask 任务从 PDF 重建内存索引（paper-qa 原生行为），大库可后续引入 `Settings.agent.index` 落盘索引目录（paper-qa 原生支持）作为增量优化。
- 引用页码依赖 paper-qa `Text.name` 的 `page-dockey` 约定，部分 PDF 可能解析不出页码（返回 null，前端显示"页码未知"）。
