# T2.0 接缝 Spike 报告：基座工作流引擎扩展可行性

- 分支：`feature/p2-T0-spike`（基线 main f0063cc）；日期：2026-09-01
- 方法：通读 `packages/server/src/modules/studio/services/workflow/`（manager.ts 2459 行全量）、run-store/schema、前端画布（WorkflowView.vue 5342 行关键路径 + @vue-flow/core 1.48 源码），并新增运行级 vitest 实证（`tests/server/workflow-t2-spike-nonagent-node.test.ts`，5/5 通过，见「实证」标注）。
- 证据分级：**测试实证**（本 spike 新增运行测试）> **源码引用**（file:line）> 推断。
- 结论速览：**三个接缝全部「需小幅改动」，无一被封死**。改动集中在 server 侧 manager.ts 的两处（类型归一化门禁、执行器分发）+ run-store 一列（输出持久化），client 侧三处（type 透传、节点模板、按类型序列化）。调度器本体（DAG/循环/join/条件边/审批/预算）零改动。

## Q1 run-store 能否容纳无 agent session 的确定性节点

**结论：需小幅改动。** run-store 存储层原生可容纳（实证）；阻塞点在 manager 执行路径与输出回流，不在表结构。

### 存储层：直接可容纳（测试实证）

- 表约束：`workflow_run_node_sessions.session_id TEXT NOT NULL`（`packages/server/src/modules/studio/infrastructure/database/schemas.ts:308`）。SQLite 的 NOT NULL 允许空串，因此「无 LLM 会话」可以用 `session_id = ''` 表达，**不需要任何 schema 变更**。
- 读取层已容忍空串：`WorkflowRunNodeSessionRecord.session_id: string`（`workflow-run-store.ts:53`），行映射 `String(row.session_id || '')`（`workflow-run-store.ts:113`）。
- 写入层 `createWorkflowRunNodeSession`（`workflow-run-store.ts:439-517`）：`session_id` 是必填入参但**无空值/格式校验**；`agent` 缺省为 `''`（`:474`）。`updateWorkflowRunNodeSession`（`:519-548`）只更新 status/时间戳/error，不碰 session_id。
- 边决策与循环轮次记录完全不引用 session：`WorkflowRunEdgeEvaluationRecord`（`:28-32`）、`WorkflowRunLoopEpochRecord`（`:34-37`）。
- **测试实证**（spike 测试 #4）：对 `status: 'running'` 的 run 写入 `session_id: ''`、`agent: ''` 的节点执行行，更新为 `completed` 并完整读回，全部成功。

### 执行路径：三处硬耦合需要分支（源码引用）

manager.ts 的节点执行器（两个孪生实现）把「执行节点」等同于「跑一次 agent 会话」：

1. **会话创建**：`executeNode` 先 `randomUUID()`（`manager.ts:1467`），`ensureWorkflowNodeSession` 经 `createSession` 落一张真正的聊天会话行（`manager.ts:1328-1349`），再连同 `session_id` 写入 run-store（`manager.ts:1489-1497`；DAG 版 `:1997-2012`）。
2. **执行分发**：`resolveWorkflowNodeRunTarget(node.data.agent)`（`manager.ts:1469`，DAG 版 `:1971`；函数本体 `:235-276`）只认五种 agent，其余抛错；随后无条件调用 `runWorkflowAndWait`（`manager.ts:1501-1519`，DAG 版 `:2014-2043`）——经 DI 注入的 chat-run 协调器（`public/workflow-runtime.ts:21-24`）。
3. **前置校验**：preflight 对每个节点跑 `assertWorkflowAgentDependencies` → `assertAgentAvailable`（`manager.ts:126-128`，`services/agent-availability.ts:31-44`），调用点在 `preflightWorkflowExecutionDefinition:429` 与 `preflightWorkflowRerunDefinition:500`。

### 输出回流：确定性节点的输出必须新落一列（源码引用 + 实证）

节点输出**只存在于聊天会话存储**，不在 run-store：执行后 `lastAssistantOutput(sessionId, ...)` 从 session 详情里捞最后一条 assistant 消息（`manager.ts:883-891`，调用点 `:1542`/`:2077`）；rerun 恢复已完成节点的输出同样走 `lastAssistantOutput(session.session_id)`（`manager.ts:2352-2358`）。`session_id = ''` 时 `getSessionDetail` 落空 → 输出静默恢复为 `''`（spike 测试 #4 证明空 session 行本身能存，但输出无处可放）。**这是 run-store 层唯一需要的 schema 改动**：给 `workflow_run_node_sessions` 加 `output_json`（或 `output_text`）列。

### 最小改动清单（Q1）

| 文件 | 函数/位置 | 改动 |
| --- | --- | --- |
| `manager.ts` | `normalizeWorkflowNode`（:284-349） | 放行 `script`/`validate`/`render` 类型，各自 data 归一化分支（agent 分支保持原样） |
| `manager.ts` | `WorkflowNodeSnapshot.data`（:106-124） | data 载荷放宽为按 type 的联合/可选字段 |
| `manager.ts` | `executeNode`（:1459-1574）与 DAG 执行器（:1968-2129） | 按 `node.type` 分发：非 agent 走确定性执行器（子进程），跳过 ensureWorkflowNodeSession/createSession/runWorkflowAndWait |
| `manager.ts` | `assertWorkflowAgentDependencies`（:126-128） | 跳过非 agent 节点（或按类型校验依赖） |
| `workflow-run-store.ts` + `schemas.ts` | `WORKFLOW_RUN_NODE_SESSIONS_SCHEMA`（schemas.ts:298-320） | 新增输出列 `output_json TEXT NOT NULL DEFAULT ''`（迁移基础设施已有先例：schemas.ts:1185-1215） |
| `manager.ts` | 输出捕获（:1542/:2077）与 rerun 恢复（:2352-2358） | 非 agent 节点改为读写新输出列 |

`buildNodeUserMessage`（:2413-2451）无需改：`skills/images` 为空数组时对任意节点都能拼出合法输入（`stringArray` 已兜底，`manager.ts:278-280`、`:343-344`）。

## Q2 rerun 快照机制对扩展节点类型的行为

**结论：需小幅改动**（与 Q1 共用改动清单；rerun 机制本身对扩展类型是友好的）。

### 快照冻结了什么

`runNow` 在持久化 run 时经 `workflowRunSnapshotGraph`（`manager.ts:161-205`）冻结（`manager.ts:2226-2243`，落库 `workflow-run-store.ts:259-283`）：

- **nodes**：归一化后的 `WorkflowNodeSnapshot`（含 `type`、position、data 全量）+ 授权视图字段（position/dragHandle/style）。注意冻结的是**归一化结果**，因此 normalize 放行新类型后，快照自动携带 `type: 'script'` 等，无需改快照格式。
- **edges**：id/source/target + 视图字段（sourceHandle/targetHandle/type/animated/label）+ 规范化 `data.orchestration`。
- **compiled_loops**。

### rerun 时类型校验在哪一步、会不会再次被拒

会。且在**第一步**：`rerunFromNode`（`manager.ts:2287-2411`）→ `preflightWorkflowRerunDefinition`（`:434-503`）→ `compileWorkflowGraphPreflight(args.run.snapshot_nodes, ...)`（`:449`）→ 逐节点 `normalizeWorkflowNode`（`:822`）——冻结快照被**重新归一化**，非 agent 节点在此抛 `must be an Agent node`，后续 evidence 检查（`:457-491`）根本不会执行。第二道门是 `assertWorkflowAgentDependencies`（`:500`）。

- **测试实证**（spike 测试 #5）：手工构造含 `type: 'render'` 冻结快照的 completed run，`manager.rerunFromNode` 拒绝并报 `workflow node render must be an Agent node`——证明 rerun 路径的拒绝点就是 normalize 复检，**没有第二处独立类型校验**。即：扩展 `normalizeWorkflowNode` 一处，run 与 rerun 两条路径同时放行。
- rerun 其余机制对确定性节点均类型无关：preserveStartNode 的 completed 检查（`manager.ts:461-463`）、边决策 evidence 重放（`:464-491`，决策来自 run-store 的边评估表而非 session）、执行预算（`:498`）、`executionScope: rerun:<ts>`（`:2404`）。唯一缺口是输出恢复（Q1 已列：`:2352-2358` 需改读输出列）。

## Q3 前端画布对未知节点类型的兜底

**结论：需小幅改动。** 现状是**静默改写而非报错/白屏**——比崩溃更危险（保存即销毁类型信息）。

### 现状行为（源码引用）

- 画布只注册了一个节点模板 `#node-agent`（`packages/client/src/views/hermes/WorkflowView.vue:3747-3749`），未传 `nodeTypes` prop。
- **载入路径丢弃 type**：`normalizeStoredNode`（`WorkflowView.vue:1132-1169`）→ `makeNode`（`:640-675`）硬编码 `type: 'agent'`（`:649`），且**不透传** `record.type`，同时用默认值填满 agent 字段（`:646-660`，agent 兜底 `'hermes'`）。工作流文档载入（`workflowDocumentFromRecord:1184-1196`）与 run 快照回放（`applyWorkflowRunSnapshot:1714-1736`，`:1723` 同样走 normalizeStoredNode）都经过这里。
- 后果：含 `script` 节点的工作流在画布打开时显示为一张普通 agent 卡片；用户一旦保存，`serializeWorkflowNodes`（`:1079-1101`）按 `node.type`（已被改写为 `'agent'`）回写——**类型信息被永久销毁**。这是主方案下客户端必须先行的原因（防护性透传 type）。
- vue-flow 层的真实兜底（若 type 被保留而模板未注册）：解析链为 slot `node-${type}` → `getNodeTypes`（未知类型映射为自身字符串，`@vue-flow/core/dist/vue-flow-core.mjs:7809-7816`）→ 全局组件解析（`:9431-9444`）→ 失败则 `emits.error(NODE_TYPE_MISSING)` 并回落到内置 `default` 节点盒子（`:9602` 渲染 `getNodeTypes.value.default`）。**即：一条错误事件 + 默认矩形，不崩溃、不白屏**。
- `WorkflowAgentNodeData`（`components/hermes/workflow/types.ts:12-34`）与状态徽标按 agent 卡片设计，确定性节点需要自己的卡片（至少 title/input/status 只读展示）。

### 最小改动清单（Q3）

| 文件 | 位置 | 改动 |
| --- | --- | --- |
| `WorkflowView.vue` | `makeNode`/`normalizeStoredNode`（:640-675/:1132-1169） | 透传 `record.type`（缺省 `'agent'`）；未知类型不注入 agent 默认值 |
| `WorkflowView.vue` | 模板（:3747 后） | 新增 `#node-script`/`#node-validate`/`#node-render`（可先共用一张通用确定性节点卡片） |
| `WorkflowView.vue` | `serializeWorkflowNodes`（:1079-1101） | 按 type 序列化各自 data 字段，避免把 agent 字段写进确定性节点 |

run 快照回放路径自动继承（同走 normalizeStoredNode），无需单独处理。

## 主方案总评与建议

**主方案（扩展节点类型）可行：需小幅改动，无结构性障碍。**

- 引擎侧唯一硬门禁是 `normalizeWorkflowNode` 的类型分支（`manager.ts:288-289`），且 run/rerun 两条路径共用它（Q2 实证）——一处扩展、两路放行。
- 执行器分发只有两个调用点（`executeNode` 与 DAG 执行器），全在 manager.ts 内部；DAG/循环/join/条件边/审批门/执行预算/超时 deadline 基础设施全部类型无关、零改动复用。
- `workflow-runtime` 是 DI 接缝（`public/workflow-runtime.ts:12-14`）：确定性执行器可作为第二个注入依赖（如 `runDeterministicNode`）加进 `WorkflowRuntimeDependencies`，不触碰 upstream 已有函数签名，符合《基座改动登记表》的 upstream 可同步目标。
- 现有测试基建（`tests/server/workflow-manager.test.ts:21-66` 的 mock 模式）可直接复用覆盖新类型。

**建议实施顺序：**

1. **client 防护先行**（或同批合入）：type 透传 + 未知类型只读保护。否则 server 放行新类型后，任何人用画布打开 research 工作流并保存，节点会被静默改写成 agent（Q3 的数据损坏风险）。
2. **server 存储列**：`workflow_run_node_sessions` 增加 `output_json` 列（迁移先例 schemas.ts:1185-1215），输出捕获/rerun 恢复切到新列。
3. **server 引擎**：`normalizeWorkflowNode` 类型分支 + 执行器分发（建议 `WorkflowRuntimeDependencies` 新增确定性执行依赖，script 节点 = python/node 子进程 + 结构化参数数组，复用 `withinWorkflowRunDeadline` 超时基础设施，`manager.ts:982-1004`）。
4. **client 展示**：三张确定性节点卡片（或先共用一张），接 run 状态徽标。

## 降级方案的触发条件

降级方案：research 侧自建确定性执行器，但复用基座 run-store 存储契约与画布展示，不重复造持久化/调度。

**触发条件（满足其一即降级）：**

1. upstream 同步成本失控：`normalizeWorkflowNode` / `executeNode` 在 upstream 频繁重构，类型分支的合并成本持续高于自建执行器的维护成本。
2. 执行器分发无法保持集中：若 upstream 引入的架构变化迫使非 agent 分支散落到多个调度点（违背「集中登记」约束）。
3. 确定性节点需要与 agent 节点本质不同的调度语义（如常驻进程、断点级检查点），manager 的事件循环模型无法承载。

**降级方案的可行性已被本 spike 侧面证明**（这也是它不是空谈的原因）：

- run-store 契约可直接写入：`createWorkflowRun` + `createWorkflowRunNodeSession(session_id: '')` + 边评估/循环轮次表对确定性节点完全可用（Q1 实证）；run 证据读取走 `getWorkflowRunWithEvidence`（`workflow-run-store.ts:339-348`），API 路由现成（`routes/workflows.ts:17-22`）。
- 画布展示可复用：执行器绕过 `manager.runNow` 直接写 run-store 后，客户端 run 历史/快照回放照常工作（Q3：回放路径类型无关，只要 normalizeStoredNode 透传 type）。
- rerun 快照可自管：snapshot_nodes 是 `unknown[]` 原样 JSON 冻结/恢复（`workflow-run-store.ts:90-91`），自建执行器不必经过 `normalizeWorkflowNode` 复检。
