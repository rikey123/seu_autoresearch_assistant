## 2. 安装记录与失败模式

1. **Python 3.14 + `pip install pdf2zh`**：安装成功，得到 **pdf2zh 1.7.9**。依赖树巨大（torch 2.13、torchvision、gradio 6.26、opencv、doclayout-yolo、openai/deepl/azure SDK 等，磁盘 >3 GB），全部走清华镜像无碍。
   - **运行时失败**：pdf2zh 1.7.9 的 `high_level.py` 使用 `np.fromstring`（numpy 2.x 已移除），首翻即抛 `ValueError`。
   - `pip install "numpy<2"` 在 3.14 无 wheel、源码构建失败（meson 报错）→ **Python 3.14 实际不可用**。3.13 venv 同因（numpy 1.26 无 cp313 wheel）放弃。
2. **现成环境复用**：本机 anaconda envs 中已存在 `zotero-pdf2zh-next-venv`（Python 3.12.13 + **pdf2zh-next 2.9.0**，含 `pdf2zh.exe`/`pdf2zh_next.exe` 入口），spike 真实链路直接在其上验证。

## 3. 关键发现：CLI 契约与两个发行版都不一致

T2.2 模板的 argv 契约是项目内部稳定契约：`-i <pdf> -o <outdir> -s <service> -lo <lang>`（结构化数组、shell:false、支持 Node 包装脚本）。实测两个发行版的原生 CLI 都不接受它：

| 发行版 | 输入 | 输出目录 | 服务/目标语言 | 其他 |
| --- | --- | --- | --- | --- |
| pdf2zh 1.7.9 | 位置参数 `files`（**`-i` 是 `--interactive`**） | **无 `-o`**，产物写在输入旁 | `-s`/`-lo` 与契约一致 | numpy 2.x 运行时崩溃 |
| pdf2zh-next 2.9.0 | 位置参数 | `--output` | `--lang-out` + 布尔服务旗标（`--google`/`--openai`/…） | 产物命名 `<stem>.<lang>.mono/dual.pdf` |

**推荐生产调用方式**：保持 T2.2 契约不变，`PAPER_TRANSLATE_PDF2ZH_BIN` 指向一个 **Node 适配包装脚本（.cjs）**——契约 argv → 所装发行版 CLI 的翻译层 + 产物命名归一化（2.x 的 `<stem>.<lang>.mono.pdf` → 契约的 `<stem>-mono.pdf`）。这正是 `PAPER_TRANSLATE_PDF2ZH_BIN` 支持包装脚本机制的设计意图；服务端代码因此对 pdf2zh 版本演化免疫。spike 适配器样例见验证环境 `%TEMP%\pdf2zh-spike\pdf2zh-contract-adapter.cjs`（约 40 行，核心逻辑已内化到 gated 测试与本文档）。

## 4. 真实链路验证（证据）

首次试跑在布局模型下载处失败（huggingface.co 超时）；设 `HF_ENDPOINT=https://hf-mirror.com` 后全程通过：

- 输入：单页英文 PDF（"The Research Workbench translates academic papers. / A persistent job queue runs the pdf2zh sidecar."）
- 命令：`pdf2zh-contract-adapter.cjs -i sample.pdf -o out -s google -lo zh` → pdf2zh-next 2.9.0
- 产物：`out/sample-dual.pdf`（38 KB）、`out/sample-mono.pdf`（38 KB）
- 内容核验（pymupdf 提取）：
  - mono（纯译文）：`研究工作台翻译学术论文。 / 持久作业队列运行pdf2zh sidecar。`
  - dual（同页双语）：`The Research Workbench translates academic papers. / 研究工作台翻译学术论文。 / …`

**自动化实证**（本分支新增）：`tests/server/research-translation-queue.test.ts` 共 15 用例——14 个 stub 管线用例 + 1 个 `PAPER_TRANSLATE_E2E_PDF2ZH_BIN` 门控真实链路用例。设门控变量后 **15/15 通过**（真实用例 61.6s，从队列 HTTP API 提交 → worker spawn → pdf2zh-next google 翻译 → 契约命名产物落盘 → job completed 全程）。不设门控时 14/14 通过、1 skipped（CI 无需 Python/网络）。

## 5. 剩余阻塞与生产化步骤

- **OpenAI 兼容后端**（`-s openai`，T2.2 默认）：链路与 stub/真实链路同一契约，只差真实 `OPENAI_API_KEY`；密钥只经环境变量传递（`OPENAI_API_KEY`/`OPENAI_BASE_URL`/`OPENAI_MODEL`），服务端不落盘、不内置模型。无 key 时任务按设计 failed 并给出明确错误（有测试覆盖）。
- **部署清单**：Python 3.10–3.12 venv + `pip install pdf2zh-next`（或复用 1.x 需钉 `numpy<2`）；`PAPER_TRANSLATE_PDF2ZH_BIN` 指向契约适配器；GFW 环境预设 `HF_ENDPOINT=https://hf-mirror.com`（仅首次模型下载需要）。
- **人工复现步骤**：
  1. 激活含 pdf2zh-next 的 Python env（或按上节新建）；
  2. `export HF_ENDPOINT=https://hf-mirror.com`；
  3. 写契约适配器脚本（`-i/-o/-s/-lo` → 位置参数 + `--output/--lang-out/--<service>` + 产物重命名），`export PAPER_TRANSLATE_E2E_PDF2ZH_BIN=<适配器绝对路径>`；
  4. `npx vitest run tests/server/research-translation-queue.test.ts` 应 15/15（含真实链路用例）；或直接 `node <适配器> -i <某真实论文.pdf> -o out -s google -lo zh` 后打开 `out/<stem>-dual.pdf`。

## 6. 对本仓库实现的影响

- 队列服务按 T2.2 契约 spawn（结构化 argv、shell:false、包装脚本以当前 Node 执行、超时 kill 进程树），与 paper-translate 工作流模板完全互通。
- spike 结论未改变服务端设计：契约不变、适配差异全部收敛在 `PAPER_TRANSLATE_PDF2ZH_BIN` 边界之外。
